# 2.0.5 性能与长时验证

运行代码经 [125 分钟真实验证](https://github.com/springs59/FGO-Max-Bond-Team-Setup/actions/runs/38331597730)，源提交为 `8c02377b0496f2c89047870657a5ea7acee77b04`。后续提交仅调整基准脚本、工作流请求和文档，运行代码保持一致。Windows、Android 安装、覆盖升级、本地数据保留和 CI 已通过。

## 与正式 2.0.0 对比

[同机完整基准](https://github.com/springs59/FGO-Max-Bond-Team-Setup/actions/runs/38346977542) 使用正式标签 `native-v2.0.0`、`native-v2.0.4` 及优化版源码；输入均取同一份当前目录的 30 位可用从者和 36 张羁绊礼装，自由配队、COST 95、精确库存曲线求解。

纯求解每组 20 次查询，预热一组后测三组中位数。2.0.0 没有新版的 `skipResultCache` 参数，因此每个计时查询使用新的有效 B 值，避免旧版完整答案缓存命中影响比较。全部 80 次结果逐一一致。生产 Worker 测试为每个版本、每轮建立独立空浏览器上下文，开启正常保存和缓存行为，三轮中位数；前两次改变条件，第三次重复第二次条件并切换账号标识。两版最优收益逐一一致。

| 环节 | 2.0.0 | 优化版 |
| --- | ---: | ---: |
| 20 次新条件纯求解 | 1890.7 ms | 1779.5 ms |
| 首次生产 Worker 完整结果 | 292 ms | 1085.4 ms |
| 修改条件后的完整结果 | 170.9 ms | 370 ms |
| 重复同条件结果 | 168.2 ms | 100.6 ms |

纯求解接近 2.0.0，本次样例中耗时低约 5.9%。完整流程仍有保存全部候选、通用方案、校验和传输的成本；首次查询及变更条件的总时间尚未恢复到 2.0.0。重复查询精确复用通过，优化版不重新搜索。以上是固定样例与对应环节的实测，不代表任意输入、设备或两小时复杂查询的整体速度；也不把缓存命中算成纯求解速度。

| 64 条重复候选入库 | 19.9 ms | 17.7 ms |

方案读取利用已有主键范围，无数据库升级或账号分库。候选保持固定 256 KiB 写缓冲及 1 MiB 编码区，缓冲满只写磁盘，按一秒检查点、明确结束或关闭同步；完整日志格式及内容不变。候选公共空库存摘要复用，重复检查只读主键。Worker 每条记录只序列化一次，普通字段减少描述符分配；继承属性、特殊属性与类型化视图保留安全处理。64 KiB 数据块确认、错误和取消释放不变。

6 万条候选完整字节数均为 87390004，逐条恢复与顺序核对通过，无不完整尾部。大消息均为 239 块、15547626 字节，别名、循环引用和内容一致；本轮编解码耗时基本持平。没有通过减少已实际计算候选、改变公式、删除库内容或去掉内存保护提速。

## 真实 125 分钟验证

使用同一 Chromium Worker、真实墙上时钟和单调时钟，连续实际求解多次不同条件，并逐一进行独立曲线结算对照。输入取实际目录前 120 位可用从者、24 张羁绊礼装；每个返回编队对 B=0..131071 的曲线值与原始结算核对。使用真实 OPFS/IndexedDB，浏览器 JavaScript 堆参数为 512 MiB；每 30 秒采样整个浏览器进程树 RSS，不强制 GC。
