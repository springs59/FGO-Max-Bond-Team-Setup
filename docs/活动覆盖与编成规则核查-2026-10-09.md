# 活动、礼装与编成覆盖核查

“六槽己方 / 无助战”表示最多可以使用六位己方从者，不表示必须填满。仅当关卡元数据明确给出 mySvtNum / svtNum 的 equal 6 限制，才要求对应人数。用户锁定为空的槽位始终为空，不提供礼装或光环。

## 已实现

- 原软件继续逐从者累加活动自身 / 全队加成，礼装按实际灵基特性逐张、逐目标结算。不同成员可同时获得不同倍率，包括多个 +100%、+50% 的数学情况。
- 空位锁定进入查询、持久化、容量、站位和结果装配；受限条件不复用不相符的默认曲线或预计算结果。
- 关卡快照保留 flags、restrictions、系统助战成员 / 固定礼装 / 满破状态 / 解锁条件。noSupportList 且无 NPC 时不借助战；存在系统助战时采用对应成员及固定装备；正常关卡可用好友助战，有合法系统助战选项时也比较系统方案。固定助战站位进入前后排计算。
- 解锁状态可从 userQuest 已通关记录核对。无法验证的 NPC 解锁条件不假定为已满足。多名强制系统助战、多件固定系统装备、未支持的其他编成限制会明确提示，不输出伪称合法的方案。
- 旧关卡 Nice 详情 404 时保留权威 raw 羁绊数据，将该关卡编成规则标为不可读取；不会假定没有限制，也不会中断其他关卡刷新。网络错误与其他 HTTP 错误继续使刷新失败，保留上一版完整数据。
- 原始 NPC 的 openedAt / closedAt 同时参与筛选和运行时检查，未来预留或已过期助战不进入当前可用集合。
- 通用预计算仅缓存后排第六位为好友助战的普通编成；无助战、系统助战、固定站位、人数限制与未知规则单独求解或明确拒绝。跳过范围写入 skippedPartyQueries，不把通用缓存宣称为这些关卡的合法结果。
- 抓包库存读取限定为己方库存表，好友 userSvtLeader、历史 userEventDeck / userQuestRecord 不作为己方持有数量、等级或满破来源。
- 已知活动有效期与被动自身时间窗同时检查。长期开放到 2038 的旧技能不会因为选择旧活动编号而重启；区服、活动编号及关卡作用范围继续参与匹配。关闭活动的旧活动评分缓存不用于结算。

## 特殊活动的账号选择：仍未完成自动识别

抓包的 userEvent 表保留了历史活动，value / flag 是不透明状态，不能把其中数字直接当作从者 ID 或羁绊倍率。导入结果只记录事件存在性及更新时间，selectionStatus 明确为 unavailable，不将历史表转换为当前加成。

本次检查的登录抓包包含 168 条 replaced.userEvent 与另外 2 条 updated.userEvent。未找到能验证本次用户“选定从者额外羁绊”的记录。好友 eventSvtPointInfo 不能作为己方所选状态。

静态活动名单中的 targetIds 代表活动固定受益名单，不能等同于用户自行选中。活动名称（例如白情）不足以确定机制。对于真实存在的锁定巧克力、伙伴等级等账号动态机制，还需对应年份、规则与可验证字段；当前不会自动推断。

## 曲线工具的覆盖边界

完整 CN/JP 身份、灵基、礼装与组合要素保留。新增：

1. 固定真实成员 / 灵基的笛卡尔展开：每个己方槽位独立选择声明的活动倍率；每个装备槽位独立选择声明礼装与满破状态，可包含多个条件礼装、全命中礼装和不装备。保留锁定空位。声明范围遍历结束才标 complete；停止或异常是 partial。
2. 条件全队礼装命中见证：按真实目录的目标特性选择不同身份的成员，检查可实现的命中人数、前后排命中位置、装备张数及满破状态；用选定全命中礼装补充其他装备槽。每张礼装的实际命中位置均由原引擎记录。
3. 将选定结果加入同图，独立显隐，继续按不同基础羁绊精确比较；可导出完整生成参数、逐槽函数与完成范围。

这些是明确范围内的遍历 / 见证，不是全部身份队伍、全部账号约束的静态最优包络。人工填写活动倍率的结果属于参数实验，尚不证明游戏实际授予该倍率。原函数仍保留两次向下取整、前后排、助战、15 绊、茶壶与固定加成。

## 验证

新增回归覆盖：好友 / 历史编队不污染库存；历史活动时间与不同活动 ID 隔离；无助战一人可成立；指定空位保持为空；元数据真的要求 equal 6 时才执行人数限制；系统助战固定成员、前排站位、固定礼装及未满破效果；未知 NPC 解锁状态拒绝使用；每个己方活动倍率位置展开。
