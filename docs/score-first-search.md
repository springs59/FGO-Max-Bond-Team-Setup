# 先找高收益，再补全同分队伍

此前的完整同分搜索在一次遍历中同时提高收益和收集队伍。收益上界等于当前最好分数的分支也会展开，因此大量当前同分方案可能拖慢寻找更高收益及证明最高分。

现在明确分成两个阶段，沿用当前精确求解器及全部关卡规则。

1. **优先找高收益并证明最高分**：先保留 AI 合法起点或有预算限制的首套合法队伍预览。普通、冠位、NPC 和扩展规则搜索优先尝试估计收益较高的从者与礼装。可安全计算上界的分支，若上界不能严格超过当前最好收益，直接跳过。只有严格改善当前最好收益的方案在这一阶段归档；每次改善立即通知界面。估计只决定访问顺序，不能用来排除队伍。
2. **补全最高分队伍**：所有候选域均完成第一阶段后，才标记最高分已经证明。固定最高分为目标，重新允许上界等于目标的分支，保留全部同分方案、不同 COST、形态、满破状态、站位和库存联动。第一阶段保留的最终最高分方案不会重复登记。只在第二阶段完全结束后，才标记同分队伍已收齐。

## 补全时出现更高收益的自动恢复

正常情况下，第一阶段已证明最高收益，补全不应再出现更高分。若精确搜索给出反例，现在不会直接报错停止，而是：

1. 立即显示新高收益队伍，撤销原最高分证明，进入重新优化阶段。
2. 关闭本次查询的分数上界剪枝，从第一个候选域重新核查。已经证明的编队规则、库存、COST 和等效替换约束继续生效；不切换旧算法，不重复调用 AI。
3. 原先已归档队伍按新分数自动归入“途中其他队伍”，新高收益队伍只归档一次。
4. 所有候选域重新搜索结束后，才恢复最高分证明，再收齐新最高分的全部同分方案。如再次出现更高分，重复上述恢复。

恢复期间停止仍保留新队伍，即使还没来得及写入归档，也能作为预览查看和导出。`recoveries` 记录恢复次数，`maximumProven` 与 `complete` 分别记录重新证明和补全状态。恢复会增加计算量；不再使用被反例推翻的分数剪枝。与该反例无关的结算、存储错误仍按原错误处理，不能伪装为完整结果。

大量低收益/当前同分记录不会占用第一阶段的归档时间。此前严格改善过收益、后来被更高分替代的方案仍在“途中其他队伍”中；如果直接达到最高分，该类别可以为零。没有数量上限或旧方案切换。

停止与导出分别保留两个事实：

| 停止位置 | 当前结果 | 最高分是否证明 | 同分队伍是否收齐 |
| --- | --- | --- | --- |
| 寻找更高收益时 | 已得到的合法预览、已归档改善方案 | 否 | 否 |
| 刚证明最高分、尚未归档同分结果 | 最高分预览仍可查看、导出 | 是 | 否 |
| 补全同分队伍时 | 已归档队伍可分页、切换、导出 | 是 | 否 |
| 两阶段均完成 | 全部最高分方案 | 是 | 是 |

结果标题、进度、停止说明和 JSONL 头的 `maximumProven` / `complete` 保持一致。完整结果才能复用；停止或写入失败不会被当作完整缓存。

## 对照结果与限制

[原始对照数据](score-first-benchmark.json)由 `scripts/benchmark-score-first.mjs` 生成。对照基线为冠位联动修复分支 `4a07d846bdcf85eda8e716d23b5191aa818a7068`，测试人工小规模队伍，关闭等效压缩，采用三轮中位数。两种方式的最高分、全部同分队伍数量及队伍指纹均一致。

| 测试场景 | 最高分 / 同分队伍数 | 旧方式证明所需节点 | 新方式证明所需节点 | 首次找到最终最高分所需节点：旧 → 新 |
| --- | --- | ---: | ---: | ---: |
| 普通条件加成 | 4220 / 648 | 7995 | 2604 | 25 → 20 |
| 舍入导致大量同分 | 3 / 25272 | 17208 | 11 | 10 → 10 |
| 冠位 | 2150 / 54 | 446 | 446 | 26 → 24 |
| 扩展出战人数规则 | 2738 / 36 | 465 | 205 | 73 → 20 |
| 实时活动加成 | 4416 / 324 | 6612 | 6612 | 304 → 299 |

旧方式直到收集结束才声明最高分已证明，因此表中旧证明节点包含收集阶段。首次找到最高分和证明最高分是不同指标。

此次改变优先级，不承诺所有输入更快完成。不能安全使用分数上界的冠位、NPC、适用活动加成仍按精确结算搜索，证明可能依然很慢。二阶段可能重复计算，收齐全部同分队伍的总耗时可能增加；上述五个小样本的总耗时中位数均有所增加。原始数据包含首个最高分时间、证明时间、归档量和最终总时间，不代表用户实际账号或手机耗时。

复现时准备基线仓库（包含原 `src`、`src/data`、`generated`、`native`），执行：

```sh
FGO_SCORE_BASELINE=/absolute/baseline/src/recommend.js node scripts/benchmark-score-first.mjs
```

验证：

- `npm test` 全套通过；新增独立穷举对照下的阶段顺序、严格改善、证明状态与跨阶段去重断言。
- 1000 组随机独立穷举对照：最高分及全部 232234 套同分队伍一致，684918 个参考完整组合；正常样本没有意外触发恢复；包含普通、活动、主练、COST、库存、形态、满破等组合。
- 原 72 组冠位穷举的 15462 套同分队伍，以及 22 组固定冠位自动/手动关联结果一致。
- 288 组首套可行性穷举、117 组扩展规则、20 组等效压缩独立展开对照通过。
- 196 组冠位压力和 384 组关卡族首套队伍检查通过；当前 CN/JP 4032 个阶段记录及 829 个扩展阶段规则首套见证检查通过。此项验证首套可行队伍，不表示所有账号的最优搜索已完成。
- 实际 Chromium/Worker/OPFS：先证明后补全，补全阶段停止仍保留已证明最高分、分页和导出；初始预览停止、无结果停止、冠位联动、NPC/阶段切换及桌面/手机宽度回归通过。

自动恢复专项验证：

- `src/solver/score-team-phases.test.js` 注入错误初次证明和连续两次反例，覆盖总收益/主练目标、预计算分数/精确结算、跨域回到起点、全部最终同分、历史保留与去重。
- Worker 在发现新高分、写入新队伍、重新证明、重新补全等节点停止，验证预览、分类、分页、导出和完整后缓存复用。另有 130 套旧同分队伍的跨页保留验证，覆盖恢复后停止及正常完成。
- 实际 Chromium 测试仅在拦截的测试模块中跳过初次优化，使用真实配队与精确结算触发恢复；最终 360 分的 36 组队伍与正常搜索一致。另一次恢复停在 363 分预览，界面及导出均撤销最高分证明，保留新队伍。
