本次发布（2.1.13）：优化 Grand、活动加成与特殊编成关卡的精确配队搜索。

增加安全分数上界、查询内礼装效果缓存及可逆的成员/席位等价分组。证明最高分时减少不影响得分的礼装排列和未固定羁绊位选择；收集阶段恢复全部合法同分选择，并分别校验礼装身份、满破与共享库存。免费 Grand 奖励位不会被普通 COST 余量错误排除，自身/条件/活动效果仍按原有规则精确结算。

同机三轮核心搜索中位数：条件礼装 Grand 从 2 秒未完成降到约 28 毫秒；活动场景从 463 毫秒降到 53 毫秒；特殊人数限制从 2 秒未完成降到 389 毫秒。上述测量不含界面和磁盘归档，不保证所有设备或账号同样提速。真实全图鉴普通/Grand 在 2 秒短测内仍有未证明最优的场景，搜索继续进行；不能将暂定收益当作全局最高分。完整数据与复现命令见[优化报告](https://github.com/springs59/FGO-Max-Bond-Team-Setup/blob/main/docs/grand-safe-bounds-20261025.md)。

验证：105 个独立 Grand 案例保留全部 27,168 套最优物理队伍；1,000 组独立随机对照保留全部 232,234 套最优物理队伍。另通过 8 个特殊规则对照、40 项四模型结果集合对照、七职阶与特殊关卡首队检查，以及真实 Worker、OPFS、分页、Grand 停止后保留首队、完整分组导出和升级回归。

保留高收益优先、完整最优证明、全部同分队伍、停止后保留结果与导出。三个 AI 模型不变，默认关闭，每次新查询最多调用所选模型一次。覆盖升级保留账号与设置。

电脑和安卓共用配队规则，分别保留国服、日服数据。

软件升级：任务中心的“软件版本”检查仓库正式 Release，启动时及每 6 小时自动检查，可单独关闭。点击下载后显示进度，支持暂停及续传，完整 SHA-256 校验后才能升级。Windows 点击“退出并升级”原位覆盖安装并重新打开；Android 点击“覆盖升级”后由系统确认，首次需允许本应用安装软件，并校验包名、版本和现有签名。覆盖升级保留账号、设置、数据及本地计算缓存，不需要卸载。旧版尚无此入口，或者 Windows 0.1.6/0.1.7 出现“Redirect was cancelled”时，需要手动下载新版 EXE 并覆盖安装一次；之后可继续使用软件内更新。

配队求解器与曲线：软件内包含编队条件、活动效果、曲线检查三页联动和精确核实。读取当前区服的数据及完整特殊编队规则；优先复用有效的本地资料域、计算缓存，条件变化后重新求解。

2.1.2 计算范围：按 2.1 功能发布，普通查询不自动匹配或拟合方案库，不写逐候选临时日志，也不自动归档候选。已完成结果使用有界缓存。暂停大规模预计算；本次未上传训练数据集。

AI 模式：默认“不使用 AI”，直接运行精确求解器。可在页面下方选择“经典高起点 AI”“扩展策略 AI”或“大数据神经 AI”，每项均显示功能特点。选择保存到本机，下次新查询生效；三模型权重随安装包提供，离线可用。启用时建议优先经典高起点 AI；扩展策略 AI 从更丰富策略中选择起点，大数据神经 AI 在公开图鉴测试中起点较高、未见组合可能退化。每次新查询最多调用所选模型一次，缓存命中不调用，最终收益与COST由精确求解器核实；起点更高不保证更快。更新或恢复权重不会开启 AI，也不改变模式选择。详见[三模型使用说明](https://github.com/springs59/FGO-Max-Bond-Team-Setup/blob/main/docs/ai-query-model-choices.md)。

Windows：运行 EXE 安装。更新窗口的“返回配队”会切回原配队窗口并保留当前配队状态；再次打开更新界面复用同一窗口，反复往返不会累积窗口。关闭主窗口后在托盘继续运行，从托盘打开“更新与后台任务”。退出软件会结束后台任务。安装包目前未使用商业代码签名证书。

安卓：下载 Release 附件中的 APK 安装。发布的 APK 已通过签名校验，并沿用原安装包的签名证书。任务通过 WorkManager 在后台执行，通知栏显示进度及暂停操作；自动检查由系统调度，允许中断和继续，不承诺持续唤醒手机。

界面：顶部“界面设置”可切换橙棕色版、白色版，以及一页式、分区多页式布局。两类选择可以自由组合。可自定义页面背景、面板、文字与强调颜色，上传本地背景图片，并恢复主题颜色或移除图片。设置在本机保存，刷新、切换区服和配队模式后仍保留。

推荐：同总羁绊归为一个标签，不同内部配队使用子标签；可加入队伍对比，查看高亮的成员、形态、礼装、COST、逐位羁绊与对其他队员的增量。任意从者位的名字可打开详情并换用；等效性包括提供的 Buff，“已上场”按身份即时刷新。选择关卡不聚焦基础羁绊输入框。账号库存、COST、满破和关卡条件仍分别校验。

数据更新：每 6 小时检查已发布的验证快照。目录锁定源提交，逐文件校验 SHA-256，只下载变化的文件；全部通过验证及本地预计算后原子切换。失败保留旧数据，暂存步骤可恢复。

可选预计算仓库：通过“全局方案／计算库 → 下载预计算方案库（可选）”下载，文件不装入 EXE、APK 或 Pages 资源包。本批发布期间暂停扩仓；用户验证并明确允许后才重新规划全 COST 批次。详见 [账号匹配、曲线与队伍对比](account-matched-curves.md)。

本地索引：在数据更新时分别生成、校验 CN/JP 的礼装、活动和编队条件联合因子索引；软件构建仅复制更新产物。公共索引保留全部身份，各本机账号再筛选可用身份、解锁灵基和库存，查询时应用 COST、锁定和助战条件进行精确求解。未变化的数据和账号复用索引，活动变化优先复用基础礼装因子。任务中心显示是否需要预计算以及预计用时范围，首次为初步估算，随后使用本机实际记录校准；下载时间另计。详见 [数据更新时联合与多账号](update-joint-multiaccount.md)。

多账号：可导入、切换、重命名或单独删除本机账号；“更新当前账号”替换其库存并保留设置。多个文件和 Chaldea 的多个 users 分别保存，不合并库存。账号的 COST、关卡、锁定、筛选、茶壶和配队模式分别保存。

离线：图鉴和配队数据包含在安装包内；首次无网络仍可计算。立绘当前使用在线资源，未浏览过的图片无网络时不保证显示。

隐私：账号抓包和导入信息不会用于更新请求，不发送到 GitHub 或第三方计算服务。

开发：先运行 `node scripts/build-native-assets.mjs`；桌面端 `cd native/desktop && npm ci && npm start`；安卓端以 JDK17、Gradle8.11.1 构建 `native/android`。Android 8 以上，须有支持模块 Worker 的较新系统 WebView。签名密钥不进入公开仓库。

验证包含：双区服本地预计算、未变化数据不重算、损坏下载拒绝发布、中断恢复、原子提交、页面固定数据版本、Windows 后台任务启动、Android 模拟器后台预计算，以及现有网页回归测试。

自动发布：在 Actions 中手动运行“完整更新并发布安装包”，或确认发布后显式更新主分支的 `.github/native-release-request.json` 时发布。请求文件只用于记录一次明确的发布要求；不得由数据更新脚本修改。请求默认先更新国服/日服资料和校验索引，再锁定提交构建 EXE 和 APK；功能发布可在请求中显式设置 `refresh_data: false`，使用现有已验证快照，跳过数据重算。两端测试和安卓签名校验全部通过后，将安装包与 SHA256SUMS.txt 同时发布到对应版本的 Release。未修改发布请求的普通主分支提交、每 6 小时刷新、每周深度刷新，以及单独运行安装包构建工作流都不发布。验证分支只构建和测试。全量更新前检查签名配置，缺少密钥时明确停止，不覆盖现有 Release。

操作入口：Actions → 完整更新并发布安装包 → Run workflow → 选择 main。安卓签名密钥只需首次配置，之后发布过程由 Actions 完成。

版本递增：每次新触发大更新，使用该工作流的运行序号递增补丁版本和 Android versionCode。第 1 至第 9 次对应 0.1.0 至 0.1.8；按用户要求，第 10 次起改为 2.0 系列，标准版本为 2.0.0，Android versionCode 为 10，后续依次为 2.0.1/code 11、2.0.2/code 12。版本名称与起始运行序号由 `native/release-version.json` 指定，Android 升级序号继续递增。失败的运行可能留下版本号空档；重跑同一次运行沿用原版本号。两端版本在构建时同步写入，仓库中的 0.1.0/code 1 保留为历史序号计算基准；验证构建使用当前版本策略的起始版本。先创建草稿，EXE、APK、校验文件全部上传并检查后才公开新 Release；旧版本保留，只允许同一次运行重试自己的附件。不要重置大更新工作流的运行序号。

维护者首次设置：在仓库 Settings → Secrets and variables → Actions 中设置 `ANDROID_SIGNING_KEY_BASE64`（原 PKCS12 签名密钥文件的 Base64）和 `ANDROID_SIGNING_PASSWORD`（原密钥密码）。密钥别名为 `fgo-bond`，证书指纹必须匹配现有 APK。密钥及密码不得提交到仓库。
