电脑和安卓共用配队规则，分别保留国服、日服数据。

软件升级：任务中心的“软件版本”检查仓库正式 Release，启动时及每 6 小时自动检查，可单独关闭。点击下载后显示进度，支持暂停及续传，完整 SHA-256 校验后才能升级。Windows 点击“退出并升级”原位覆盖安装并重新打开；Android 点击“覆盖升级”后由系统确认，首次需允许本应用安装软件，并校验包名、版本和现有签名。覆盖升级保留账号、设置、数据及本地计算缓存，不需要卸载。旧版尚无此入口，或者 Windows 0.1.6/0.1.7 出现“Redirect was cancelled”时，需要手动下载新版 EXE 并覆盖安装一次；之后可继续使用软件内更新。

配队求解器与曲线：软件内包含编队条件、活动效果、曲线检查三页联动和精确核实。读取当前区服的数据及完整特殊编队规则；优先复用有效的本地资料域、计算缓存，条件变化后重新求解。

聚合方案／计算库：用户完成的查询、实际算出的候选和曲线汇入同一个本地库，包括非最优候选及等效曲线的已生成变体，相同内容自动去重。未展开或被剪枝的组合不会为了保存而额外穷举；搜索期间的中间 DP 状态不作为完整编队保存。通用方案只保存成员、灵基、礼装、满破要求和位置，不绑定账号、库存、羁绊状态或旧收益；自由配队和所有账号共同调用，按当前库存、活动、关卡及 COST 重新核实。可从整个普通方案库检索适配编队，按当前条件比较合法方案；库内调用不宣称整个搜索空间的当前最优；冠位及固定系统助战方案会保存供迁移，但暂不支持普通方案直接调用。

自动复用：完整有效输入相同时直接读取旧答案；输入改变时，以重新结算后的合法通用方案帮助精确搜索，库存新增时仍核算新最优。导出整个库只生成一个压缩文件，可在网页、EXE、APK 之间迁移并合并。通用编队本身不携带账号状态。完整计算备份含当次计算槽位与收益，不含登录回包。重复去重，同条件不同结果保留并重新核算；损坏文件整份拒绝合并，不覆盖账号和设置。新版 Android、Windows 使用分块传输和流式写入，整个库仍是一个文件，无需按记录拆分导出。导入兼容旧版备份，移除旧版一万条记录的拆分要求；解压总量上限 1 GiB、单条记录上限 64 MiB，超限或存储不足时明确报错并保留已有库。新版查询归档修订号为 2，旧答案保留供迁移，首次遇到旧修订的同条件查询时补齐新版候选归档后再直接复用。清除站点或应用数据可能移除本机记录，长期保存请自行导出。

Windows：运行 EXE 安装。关闭主窗口后在托盘继续运行，从托盘打开“更新与后台任务”。退出软件会结束后台任务。安装包目前未使用商业代码签名证书。

安卓：下载 Release 附件中的 APK 安装。发布的 APK 已通过签名校验，并沿用原安装包的签名证书。任务通过 WorkManager 在后台执行，通知栏显示进度及暂停操作；自动检查由系统调度，允许中断和继续，不承诺持续唤醒手机。

界面：顶部“界面设置”可切换橙棕色版、白色版，以及一页式、分区多页式布局。两类选择可以自由组合。可自定义页面背景、面板、文字与强调颜色，上传本地背景图片，并恢复主题颜色或移除图片。设置在本机保存，刷新、切换区服和配队模式后仍保留。

推荐：保留不同助战礼装作用与助战位置下的队伍方案，按羁绊收益排序；通过左右翻页、卡片或列表切换，查看各方案与可替换成员。账号库存、COST、满破和关卡条件仍分别校验。

数据更新：每 6 小时检查已发布的验证快照。目录锁定源提交，逐文件校验 SHA-256，只下载变化的文件；全部通过验证及本地预计算后原子切换。失败保留旧数据，暂存步骤可恢复。

预计算：在数据更新时分别生成、校验 CN/JP 的礼装、活动和编队条件联合因子索引；软件构建仅复制更新产物。公共索引保留全部身份，各本机账号再筛选可用身份、解锁灵基和库存，查询时应用 COST、锁定和助战条件进行精确求解。未变化的数据和账号复用索引，活动变化优先复用基础礼装因子。任务中心显示是否需要预计算以及预计用时范围，首次为初步估算，随后使用本机实际记录校准；下载时间另计。详见 [数据更新时联合与多账号](update-joint-multiaccount.md)。

多账号：可导入、切换、重命名或单独删除本机账号；“更新当前账号”替换其库存并保留设置。多个文件和 Chaldea 的多个 users 分别保存，不合并库存。账号的 COST、关卡、锁定、筛选、茶壶和配队模式分别保存。

离线：图鉴和配队数据包含在安装包内；首次无网络仍可计算。立绘当前使用在线资源，未浏览过的图片无网络时不保证显示。

隐私：账号抓包和导入信息不会用于更新请求，不发送到 GitHub 或第三方计算服务。

开发：先运行 `node scripts/build-native-assets.mjs`；桌面端 `cd native/desktop && npm ci && npm start`；安卓端以 JDK17、Gradle8.11.1 构建 `native/android`。Android 8 以上，须有支持模块 Worker 的较新系统 WebView。签名密钥不进入公开仓库。

验证包含：双区服本地预计算、未变化数据不重算、损坏下载拒绝发布、中断恢复、原子提交、页面固定数据版本、Windows 后台任务启动、Android 模拟器后台预计算，以及现有网页回归测试。

自动发布：在 Actions 中手动运行“完整更新并发布安装包”，或确认发布后显式更新主分支的 `.github/native-release-request.json` 时发布。请求文件只用于记录一次明确的发布要求；不得由数据更新脚本修改。它先完成国服/日服数据更新、全量预计算与验证，再锁定验证后的提交构建 EXE 和 APK；两端测试和安卓签名校验全部通过后，将安装包与 SHA256SUMS.txt 同时发布到对应版本的 Release。未修改发布请求的普通主分支提交、每 6 小时刷新、每周深度刷新，以及单独运行安装包构建工作流都不发布。验证分支只构建和测试。全量更新前检查签名配置，缺少密钥时明确停止，不覆盖现有 Release。

操作入口：Actions → 完整更新并发布安装包 → Run workflow → 选择 main。安卓签名密钥只需首次配置，之后发布过程由 Actions 完成。

版本递增：每次新触发大更新，使用该工作流的运行序号递增补丁版本和 Android versionCode。第 1 至第 9 次对应 0.1.0 至 0.1.8；按用户要求，第 10 次起改为 2.0 系列，标准版本为 2.0.0，Android versionCode 为 10，后续依次为 2.0.1/code 11、2.0.2/code 12。版本名称与起始运行序号由 `native/release-version.json` 指定，Android 升级序号继续递增。失败的运行可能留下版本号空档；重跑同一次运行沿用原版本号。两端版本在构建时同步写入，仓库中的 0.1.0/code 1 保留为历史序号计算基准；验证构建使用当前版本策略的起始版本。先创建草稿，EXE、APK、校验文件全部上传并检查后才公开新 Release；旧版本保留，只允许同一次运行重试自己的附件。不要重置大更新工作流的运行序号。

维护者首次设置：在仓库 Settings → Secrets and variables → Actions 中设置 `ANDROID_SIGNING_KEY_BASE64`（原 PKCS12 签名密钥文件的 Base64）和 `ANDROID_SIGNING_PASSWORD`（原密钥密码）。密钥别名为 `fgo-bond`，证书指纹必须匹配现有 APK。密钥及密码不得提交到仓库。
